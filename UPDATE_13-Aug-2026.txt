 1. BUG FIX - GROUP CHAT MESSAGES SHOWING "SENT WITH A DIFFERENT
    ENCRYPTION KEY" AFTER PAGE RELOAD (F5)
----------------------------------------------------------------------
Status: FIXED

Problem:
  After reloading the page, messages that displayed fine before the reload
  started showing the error "This message can't be displayed because it was
  sent with a different encryption key."

Root cause:
  Group chat messages use a chain ratchet (sender-key). On reload, the whole
  history was re-decrypted by re-deriving the sender-key chain. If the chain
  state in the browser no longer matched the history (a deleted, expired, or
  rotated key, an identity mismatch, or an out-of-order message), every
  message after the broken link failed to authenticate - and the broken chain
  was also saved back, permanently corrupting future messages.

Fix applied (client/src/context/E2EEContext.jsx):
  - Added a per-user decrypted plaintext cache in localStorage. Once a
    message is successfully decrypted, it is rendered from the cache on every
    reload, so it never depends on re-deriving the chain again.
  - handleSenderKeyMessage no longer rewinds the chain when the same key is
    already held.
  - decryptMessages skips sender-key re-processing for senders whose history
    is already fully decrypted (cached).
  - An envelope fingerprint ensures edited messages still re-decrypt instead
    of showing stale text.

 2. BUG FIX - CALL DOES NOT END ON THE OTHER SIDE WHEN ONE SIDE
    HANGS UP
----------------------------------------------------------------------
Status: FIXED

Problem:
  During a voice/video call, when one side pressed "end call", that side's
  call ended successfully but the other side's call UI stayed active forever.

Root cause:
  The call object stored in callRef.current never had a "mode" field set.
  The hangup() function checked callRef.current.mode to decide whether to
  notify the peer, but it was always undefined - so it silently ended the
  local call WITHOUT sending the call_end/call_cancel event to the server.
  The peer therefore never received the call_ended signal.

Fix applied (client/src/context/CallContext.jsx):
  - callRef.current.mode is now set at every call transition:
      * 'outgoing'  -> when starting a call
      * 'incoming'  -> when receiving a call
      * 'active'    -> on accept, on answer, and when the connection opens
  - hangup() now correctly emits 'call_end' (active call) or 'call_cancel'
    (ringing call), which the server relays to the other side.

 7. BUG FIX - SENT MESSAGES NOT VISIBLE TO THE SENDER
----------------------------------------------------------------------
Status: FIXED

Problem:
  After sending a message it never appeared in the sender's chat - but the
  receiver saw it fine.

Root cause:
  The server always broadcasts the saved message back to every member
  (sender included) over their user:<id> socket channel. App.jsx's
  handleNewMessage had an early exit - `if (msg.sender_id === user?.id)
  return;` - that discarded the sender's own echo, and ChatComposer had no
  optimistic insert, so the sender's own message never rendered.

Fix applied (client/src/App.jsx):
  - handleNewMessage no longer skips the sender's own echoed message. It now
    flows through the normal decrypt-and-append path (the E2EE layer already
    supports reading back your own messages via the embedded self-copy).
  - Own echoes still do NOT increment unread badges, do NOT play the
    notification sound, and do NOT trigger markRead.

 3. BUG FIX - APP CRASH "SOMETHING WENT WRONG" ON EVERY LOAD
----------------------------------------------------------------------
Status: FIXED

Problem:
  After the group admin/group edit work, the app showed the error
  boundary ("Something went wrong - A UI rendering error occurred") on
  every page load and was completely unusable.

Root cause:
  client/src/App.jsx: the socket useEffect listed refreshActiveRoom in its
  dependency array, but the useCallback was declared AFTER that effect.
  React evaluates the deps array during render (top to bottom), and reading
  the const before its declaration threw a TDZ ReferenceError
  ("Cannot access 'refreshActiveRoom' before initialization") on every
  render, which the ErrorBoundary caught.

Fix applied (client/src/App.jsx):
  - Moved the refreshActiveRoom useCallback above the socket useEffect that
    depends on it. Verified with a headless browser that the error screen no
    longer appears and the login UI renders.

 4. BUG FIX - LOGIN FAILING WITH "FAILED TO FETCH"
----------------------------------------------------------------------
Status: FIXED

Problem:
  Signing in reported "Failed to fetch" even though the backend was up.

Causes & fixes:
  - The vite dev server serving the client (port 3000) was stopped, so the
    browser's fetch('/api/...') hit a dead server -> network-level
    "Failed to fetch". Restarted the dev server.
  - CORS also rejected requests whose Origin was http://127.0.0.1:3000
    (only http://localhost:3000 was allowed), so opening the app via the IP
    failed on the CORS preflight. Added http://127.0.0.1:3000 to CLIENT_URL
    in server/.env and restarted the backend. Verified both origins now
    reach the API.
